# Hub 首页双对话模式设计

## 目标

将 Hub 首页恢复为两个边界清晰的模式，同时保留现有品牌首屏、首条消息后的全屏对话、流式输出、取消、身份隔离和受控 Agent 推荐卡片。

## 模式

### 普通对话

- 前端请求固定使用 `mode=instant`。
- 后端只使用简短的 Hub 身份说明并流式回答。
- 不读取路由 Skill、Agent 功能清单或运行时 Registry。
- 初始输入提示为“有什么想聊的？我会快速回应。”

### 需求分析路由

- 前端请求使用专门的流式路由模式。
- 每轮读取路由 Skill、Agent 功能清单，并与运行时 active Registry 求交集。
- 对核心演示需求先执行高置信组合匹配：期末/考试/具体课程与复习意图组合指向瀚海行，签字/盖章与地点、办理或查询意图组合指向校园公共服务 Agent；未明确命中时再调用模型语义路由。
- 命中时只返回服务端校验过的 `agent_id` 推荐卡片；前端只用该 `agent_id` 调用平台既有激活流程并依据服务端 Registry 定位，不使用模型 URL 或客户端缓存的 Endpoint。
- 未命中时在同一模式中给出普通回答，不让用户陷入无响应状态。
- 初始输入提示为“欢迎说出你的需求，我会分析并推荐合适的平台 Agent。”

## 交互与存档

- 输入框上方使用“普通对话 / 需求分析路由”分段控件。
- 当前模式没有消息时显示一句英文、一句中文的品牌 Logo；发送首条消息后切换为现有全屏对话布局。
- 左侧存档按 `user_id + mode` 隔离。切换模式后只展示该模式的记录，并恢复该模式最近的活动会话；不复制、不迁移另一模式的消息。
- 新建对话只在当前模式内生效。身份切换继续中止旧请求，避免响应写入其他身份或模式。
- 存档读取兼容旧的未分模式数据：含受控 Agent 推荐卡片的旧会话归入需求分析路由，其余旧会话归入普通对话；首次写入后固化为分模式结构，不重复迁移。

## 后端与错误处理

- 保留 `instant`、`route` 与旧 `auto` 兼容入口。
- 新增明确的流式需求路由入口，始终执行路由分析，不使用关键词前置门控。
- 路由模型失败、超时、输出无法解析或没有匹配时，安全回退到普通流式回答。
- active Registry 为空时直接进入普通回答；任何模型生成的未知 Agent ID、URL 或敏感字段均不得进入推荐卡片。
- 两个前端模式统一使用 SSE：正文使用 `model.output_text.delta`，推荐使用 `home.recommendation`，每个正常请求最终必须以 `home.completed` 收口；路由未命中时显式发送 `home.recommendation: null` 后再完成。
- 用户取消、切换模式或切换身份时中止当前流，并使用 generation guard 丢弃迟到事件；错误或异常 EOF 清除 pending 状态，空的 assistant 占位消息不得持久化。

## 验收

- 普通对话“你好”只调用一次流式模型，不加载路由说明。
- 需求路由“我要复习期末考试”推荐瀚海行。
- 需求路由“毕业论文盖章需要去哪”推荐校园公共服务 Agent。
- 两种模式的存档、活动会话和初始提示互相隔离。
- 两种模式在首条消息前显示品牌 Logo，发送后均进入全屏对话。
- 取消、错误、刷新回溯、身份切换、四 Agent 广场和瀚海行工作台不回归。
