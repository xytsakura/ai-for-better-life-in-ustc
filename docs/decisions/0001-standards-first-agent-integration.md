# ADR-0001：采用标准优先的 Agent 集成架构

- 状态：已接受
- 日期：2026-07-19
- 决策者：AI for better life In ustc 团队

## 背景

项目需要集成不同团队独立开发的校园 Agent。协议必须支持能力发现、长任务、进度、追问、流式输出和认证说明，同时让两个课程 Demo 能方便地访问评课社区、GitHub 和个人资料。

## 候选方案

### 自定义 Manifest + REST

实现速度可控，但团队需要自行定义任务状态、流式事件、认证、发现和 SDK。协议价值难以与现有生态比较，后续兼容成本高。

### MCP-only

可以把每个 Agent 包装为 MCP 工具，原型简单，但会把具备自主任务生命周期的远端 Agent 降格为一次工具调用，不适合独立 Agent 之间的协作。

### A2A + MCP + OpenAPI/JSON Schema

A2A 负责 Agent 发现和 Agent-to-Agent 任务，MCP 负责 Agent 对工具与数据源的调用，OpenAPI/JSON Schema 负责平台普通 HTTP 接口和数据契约。职责清晰，并能复用现有 SDK。

## 决策

采用第三种方案：

- 外部和内部业务 Agent 通过 A2A 接入；
- 数据源与工具通过 MCP 暴露给 Agent；
- Gateway 管理白名单、能力索引、路由和任务代理；
- JSON Schema 2020-12 是共享业务载荷的契约来源，OpenAPI 3.1 描述平台 REST API；
- OpenTelemetry 负责跨服务可观测性；
- 比赛版不依赖仍处于演进中的开放注册市场。

## 结果

正面结果：协议定位清晰，项目创新点从“自定义格式”转向“校园 Agent 的标准集成和可用治理”，第三方接入可以被真实验证。

代价：团队需要同时理解 A2A 和 MCP，并处理协议 SDK 版本变化。实施时必须先做最小端到端原型，避免在全部细节稳定前扩展两个 Demo。

## 约束

- 不把完整 Agent 简单包装为 MCP Tool；
- 不自建与 A2A 重复的任务状态机；
- 不在 A2A 消息中传递数据源 Cookie 或模型 API key；
- 不同时维护两套不同的业务 Payload 契约。

## 复审条件

若官方 SDK 无法在一周内跑通 Agent Card、任务创建和 SSE，则允许保留兼容层并缩减传输能力，但对外契约仍应尽量保持 A2A 兼容，而不是直接改为私有协议。
